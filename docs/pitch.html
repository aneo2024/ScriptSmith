业务场景

场景一：小说变成剧本

一个作者写了一部小说，想改成剧本——但他不会写剧本格式。

难在哪

剧本有固定的格式规范——slugline、对白、转场标记。小说的心理描写要变成动作和对话暗示。《百年孤独》改成剧本不必从头抄，但格式转换这件事就拦住了一大半作者。

ScriptSmith 怎么做

上传小说 → 选格式（电影/电视剧/舞台剧/动画/短片/网剧/纪录片）和风格（忠实原著/武侠/黑色电影等 11 种）→ 点转换 → 拿到初稿。77 种组合，不同题材用不同风格。

然后呢？AI 不是黑箱。每处改编都记录了备注——为什么合并两个角色、为什么删掉一段心理描写。作者可以信任，也可以推翻。初稿是你的，决定权也在你。
业务场景

场景二：让角色有血有肉

初稿有了，但人物还不够立体。郭靖长什么样？黄蓉经历了什么？

直接的问题

初稿里角色只有对白和基本介绍。要让角色"立起来"，需要外貌、性格、背景、完整人生经历。自己写人物小传？很多作者不擅长或者没时间。

产品解法

在作品详情页，作者按需点击：
• 生成角色外貌描述
• 生成作品级人物小传（长相+性格+背景，批量完成）
• 生成单个人物生平长文（400-800 字，生平轨迹+性格解析+人物评价）
• 手动编辑任何字段

为什么要把角色数据拆成字段？外貌、性格、背景各自独立——作者在编辑器可以单独改外貌不影响性格；导出 YAML 时外貌字段可以被外部工具读取；以后接 AI 生图，外貌字段直接当 prompt；以后给演员开权限，他看到的就是作者打磨好的完整小传。同一份数据，多种消费方式，这就是结构化设计的意义。
业务场景

场景三：一部作品，多集剧本

长篇小说分多集改编——每集独立，但角色设定不能前后打架。

多集创作的痛

第 1 集郭靖 18 岁，第 5 集他 25 岁了。每集剧本单独存的话，设定需要重复写，翻几集就不知道哪一版是最新的。多集创作最大的痛苦就是维护一致性。

产品怎么做

Work（作品）和 Script（剧集）分两层。稳定的属性（性别、性格、背景）存在 Work 层，所有剧集共享。每集自己的状态（年龄、弧光）存在 Script 层，各自独立。后台双向同步——信息更新了自动同步过去。用户完全无感。

体验上：一次转换就是新的一集，系统自动编号。删除一集其他集自动重排。删作品时级联删除所有相关剧集和任务。用户不用管数据存在哪层，只管创作。
支撑这些场景的设计

三个场景背后，三个设计

77 种内容组合

7 种格式 × 11 种风格。前端枚举、后端 prompt 映射、AI 输出——同一组 key 串联。加一对格式和风格只需要加数据，不改业务代码。

分步深化路径

转换 → 编辑 → 生成外貌 → 生成小传 → 生成生平 → 导出。每一步独立可选可重复。角色没整理好时 omitempty 保证文件干净体面。

两级存储 + 字段结构化

Work 层管稳定属性，Script 层管剧集状态。角色字段拆开——编辑器、YAML 导出、未来生图，各取所需。
