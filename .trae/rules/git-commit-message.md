content = """# AI 生成提交信息风格规则

> 本文件定义了 AI 辅助生成 Git 提交信息（Commit Message）时应遵循的规范与风格。
> 适用于所有由 AI 生成或 AI 辅助生成的代码提交信息。

---

## 一、基本格式

采用 **Conventional Commits** 规范为基础，结合中文团队的表达习惯：

```
<type>(<scope>): <subject>

<body>

<footer>
```

### 格式说明

| 部分      | 是否必填 | 说明                             |
| --------- | -------- | -------------------------------- |
| `type`    | ✅ 必填  | 提交类型，见下方「类型定义」     |
| `scope`   | ❌ 可选  | 影响范围（模块/组件/文件名）     |
| `subject` | ✅ 必填  | 简短描述（不超过 50 个字符）     |
| `body`    | ❌ 可选  | 详细说明（每行不超过 72 个字符） |
| `footer`  | ❌ 可选  | 关联 Issue、Breaking Change 等   |

---

## 二、类型定义（Type）

| 类型       | 含义     | 使用场景                                       |
| ---------- | -------- | ---------------------------------------------- |
| `feat`     | 新功能   | 新增功能、新增页面、新增 API                   |
| `fix`      | 修复     | 修复 Bug、修复错误逻辑                         |
| `docs`     | 文档     | 仅修改文档、注释、README                       |
| `style`    | 样式     | 代码格式调整（不影响逻辑）：空格、缩进、分号等 |
| `refactor` | 重构     | 代码重构（既不修复 bug 也不添加功能）          |
| `perf`     | 性能     | 性能优化、提升执行效率                         |
| `test`     | 测试     | 添加或修改测试代码                             |
| `chore`    | 杂务     | 构建过程、辅助工具、依赖更新等                 |
| `ci`       | 持续集成 | CI/CD 配置、脚本修改                           |
| `revert`   | 回退     | 撤销之前的提交                                 |
| `build`    | 构建     | 影响构建系统或外部依赖的更改                   |
| `wip`      | 进行中   | 工作尚未完成，临时提交（不推荐频繁使用）       |

---

## 三、语言风格规则

### 3.1 语言选择

- **默认使用中文** 编写 `subject` 和 `body`
- 专有名词、技术术语保留英文原样（如 `Vuex`, `Webpack`, `Docker`）
- 如需面向国际化团队，可切换为英文，但需全篇统一

### 3.2 语气与表达

- ✅ 使用**祈使句**，如「添加」「修复」「更新」「移除」
- ✅ 简洁明了，避免冗余词汇
- ❌ 不使用过去时（如「添加了」「修复了」）
- ❌ 不以句号结尾 `subject`
- ❌ 不使用无意义的描述（如「修改了一些代码」「更新」）

### 3.3 Subject 书写规范

```
✅ feat(user): 添加用户登录验证码功能
✅ fix(api): 修复订单查询时的时间戳解析错误
✅ docs(readme): 更新项目部署说明

❌ feat: 新功能                    ← 过于笼统
❌ fix: 修复了一个 bug              ← 未说明具体修复内容
❌ update: 修改代码                 ← 类型错误，描述模糊
```

### 3.4 Body 书写规范

- 说明「为什么修改」而不仅是「修改了什么」
- 多行描述时，每行不超过 72 个字符
- 可包含变更前后的对比说明

```
✅ 正确示例：

fix(payment): 修复支付宝回调验签失败问题

支付宝升级了 RSA 签名算法，旧版 SDK 使用的 SHA1 已被废弃。
将签名验证方式升级为 SHA256withRSA，并兼容旧版回调数据。

相关文档：https://opendocs.alipay.com/open/203/105288
```

## 四、Scope 命名规范

| 范围   | 适用场景                               |
| ------ | -------------------------------------- |
| 模块名 | `user`, `order`, `payment`, `auth`     |
| 层级名 | `api`, `ui`, `db`, `config`            |
| 文件名 | `readme`, `package.json`, `dockerfile` |
| 通配   | `global`, `all`, `deps`                |

> 若涉及多个 scope，选择最主要的一个，或在 body 中补充说明。

## 五、Footer 使用规范

### 5.1 关联 Issue

```
Closes #123
Fixes #456
Relates to #789
```

### 5.2 Breaking Change

```
BREAKING CHANGE: 移除旧版登录接口 /api/v1/login
迁移方式：请使用 /api/v2/login 并传入新的参数格式。
```

### 5.3 Co-authored-by

```
Co-authored-by: 张三 <zhangsan@example.com>
```

## 六、AI 生成提示词模板

当需要 AI 生成提交信息时，可使用以下提示词：

```
请根据以下代码变更生成符合规范的 Git 提交信息：

【变更内容】
{diff 或变更描述}

【要求】
1. 使用 Conventional Commits 格式
2. 语言：中文
3. subject 不超过 50 字符
4. 如有必要，补充 body 说明变更原因
5. 如有 Breaking Change，在 footer 中标注
```

## 七、示例集

### 功能新增

```
feat(auth): 集成微信扫码登录

新增微信 OAuth2.0 授权流程，支持 PC 端扫码登录。
包含授权回调处理、用户信息同步、Token 生成逻辑。

Closes #42
```

### Bug 修复

```
fix(dashboard): 修复数据看板图表渲染空白问题

ECharts 容器在 Tab 切换时未正确计算尺寸，导致 canvas 宽高为 0。
添加 resize 监听并在 tab 激活时手动调用 chart.resize()。

Fixes #88
```

### 性能优化

```
perf(query): 优化订单列表查询速度

将订单表的全表扫描改为基于 create_time 的索引查询，
查询耗时从 1200ms 降至 80ms。
```

### 代码重构

```
refactor(utils): 抽离日期格式化函数至独立模块

原 utils/index.js 超过 500 行，职责混乱。
将日期相关函数迁移至 utils/date.js，统一使用 dayjs 处理。
```

### 文档更新

```
docs(api): 补充用户模块接口文档

新增 /api/v2/users 接口的入参说明、响应示例及错误码定义。
```

### 依赖更新

```
chore(deps): 升级 Vue 3.2 → 3.4

同步更新相关生态依赖：
- vue-router 4.2.0
- pinia 2.1.0
- @vitejs/plugin-vue 5.0.0
```

## 八、检查清单（Checklist）

提交前确认：

- [ ] `type` 选择正确，符合变更实际内容
- [ ] `subject` 使用祈使句，无句号结尾
- [ ] `subject` 长度 ≤ 50 字符
- [ ] `body` 说明了「为什么」而不仅是「做了什么」
- [ ] `body` 每行长度 ≤ 72 字符
- [ ] 专有名词拼写正确
- [ ] 关联的 Issue 已在 footer 中引用
- [ ] Breaking Change 已明确标注
